# HDF5 转换功能需求评估与项目自定义实现说明

## 1. 文档目的

本文用于评估“以通用性更好为理由，增加 HDF5 数据转换功能”的需求，说明当前不宜直接实施的技术原因，并给出可执行的替代方案和后续准入条件。

本文的结论不是永久排除 HDF5，而是区分“项目自定义交换格式”和“兼容指定训练框架的 HDF5 适配器”。当前已实现前者，仍不宣称兼容任意训练框架。

## 2. 评估结论

当前结论：**接受项目自定义 HDF5 v1 交换格式；若要求直接兼容某个训练框架，仍需补充该框架的 schema 和验收样例。**

项目 HDF5 v1 的规范实现位于 `data_collection_pkg/dataset/hdf5_schema.py`、`hdf5_converter.py` 和 `hdf5_verify.py`。它从 `cleaned/<mode>/qpos_gripper` 流式读取 JSONL 与外部图像，输出单个 `.hdf5` 文件，包含 state/action、时间戳、双路 RGB 图像、episode 索引和语言元数据。

原因是 HDF5 是通用的二进制容器格式，不是统一的机器人学习数据标准。它规定了如何保存数组、层级结构、属性和压缩数据，但没有规定机器人学习数据中的以下内容：

- 机器人状态和动作的字段名称；
- episode 的目录组织方式；
- 图像的存储方式、通道顺序和布局；
- 动作维度、单位和数据类型；
- 时间戳和 episode 结束标记；
- 任务名称、task ID 和语言指令的存储位置；
- 训练器读取数据的接口。

因此，生成一个可以被 HDF5 工具打开的文件，不等于生成了可以被目标训练框架直接训练的数据集。

## 3. “HDF5 更通用”的技术判断

### 3.1 HDF5 是容器，不是训练协议

不同项目可以使用完全不同的 HDF5 内部结构。例如一种项目可能使用 `data/demo_0/obs/qpos` 和 `data/demo_0/actions`，另一种项目可能使用 `episodes/episode_000000/observations/state` 和 `episodes/episode_000000/actions`，也有项目使用全局 `observations`、`actions` 和 `episode_ends` 数组。

这些结构都符合 HDF5 标准，但训练代码不能自动互换使用。训练器通常会访问固定路径和固定字段，如果路径、dtype 或维度不符合预期，即使文件本身有效，也无法加载。

### 3.2 训练兼容性取决于具体 schema

要使 HDF5 能用于训练，至少需要明确：

| 项目 | 必须明确的内容 |
| --- | --- |
| 目标框架 | robomimic、旧版 ACT、自定义 PyTorch Dataset 或其他框架 |
| 状态字段 | `qpos`、`state` 或其他名称，是否包含夹爪 |
| 动作字段 | 位置、速度、增量或其他表示，维度和单位 |
| 图像字段 | RGB/BGR、HWC/CHW、原始数组或 JPEG 字节 |
| episode 结构 | 每个 episode 独立 group，还是全局数组加结束索引 |
| 时间信息 | 时间戳单位、fps、是否要求等间隔采样 |
| 任务信息 | task、task ID、语言指令和成功标记的位置 |
| 验收方式 | 官方样例、加载脚本或可运行训练 smoke test |

在这些条件未确定前，无法判断某个 HDF5 输出是否“通用”。

## 4. 与当前 JSONL 数据源的比较

当前项目将清洗后的 JSONL 作为内部规范数据源，已经覆盖 observation、action、双相机数据、时间戳、同步质量、episode 元数据、Success/Failure outcome、task ID、英文/中文语言指令、清洗结果和丢帧原因。

JSONL 也不是所有训练框架的直接输入格式，但它具有以下工程优势：

1. 字段结构透明，可直接检查和审计；
2. 增加新字段不会破坏旧记录；
3. 容易按目标框架编写转换适配器；
4. 适合保存质量问题和追溯信息；
5. 不绑定某一个训练框架的 HDF5 路径约定。

HDF5 的优势主要是二进制数组读写、随机访问、压缩和批量训练效率，而不是跨框架语义通用性。

## 5. 对当前项目的影响

当前项目已经提供原始数据采集、cleaned 数据集生成、LeRobot v3 ACT 导出、LeRobot v3 VLA 导出、episode 语言标注和 VLA 追溯报告、数据质量验证及只读回放。

在没有目标 HDF5 schema 的情况下直接增加转换功能，会产生以下问题：

### 5.1 无法保证训练可用

最多只能保证 HDF5 文件可以创建和打开，不能保证甲方现有训练代码能够读取，更不能保证动作、图像和语言语义被正确解释。

### 5.2 引入重复的数据出口

项目需要同时维护 JSONL、LeRobot 和 HDF5 三套输出逻辑。若 HDF5 的目标没有确定，后续很可能因为训练框架不同而重复开发多个互不兼容的 HDF5 版本。

### 5.3 增加依赖和维护成本

需要引入 `h5py` 及相关测试、文档、版本兼容和异常处理。新增代码本身不是主要风险，真正的风险是没有明确的下游消费者和验收样例。

### 5.4 增加语义错配风险

如果 HDF5 中只保存 `task_id`，但下游训练器需要自然语言指令，可能导致数据可以加载但语言条件缺失。若图像布局、动作维度或夹爪表示不一致，也可能产生隐蔽的训练质量问题。

## 6. 对需求的正式处理建议

建议将当前需求由：

> 增加通用 HDF5 转换功能

调整为：

> 增加兼容指定训练框架和指定数据规范的 HDF5 导出功能

并要求需求方提供以下资料：

1. 目标训练框架和版本；
2. 官方 HDF5 数据格式说明或参考数据集；
3. 目标训练代码的数据加载入口；
4. state、action、camera、timestamp、episode、task 和 language 字段定义；
5. 图像编码、排列方式和压缩要求；
6. 至少一个可成功加载的样例 HDF5；
7. 一个最小训练或数据加载验收命令；
8. 对缺失语言、失败 episode 和异常帧的处理规则。

在上述资料提供前，不建议承诺“生成的 HDF5 可直接用于甲方训练”。

## 7. 可接受的替代方案

### 方案 A：维持 JSONL 为规范源，按需提供适配器

继续以 cleaned JSONL 作为权威数据源；明确目标框架后，再从 JSONL 导出对应的 HDF5。每个 HDF5 适配器只承诺兼容一个明确的 schema。

这是风险最低、可追溯性最好的方案。

### 方案 B：先提供 HDF5 读取样例和 schema 草案

如果甲方暂时无法确定训练框架，可以先定义一个项目内部的 HDF5 schema，同时提供字段字典、group/dataset 路径表、dtype 和 shape 约束、读取示例以及 round-trip 校验脚本。

该方案只能称为“项目自定义 HDF5”，不能称为“通用 HDF5”或承诺兼容所有训练器。

### 方案 C：优先使用已有标准出口

对于 ACT/VLA 训练，优先使用当前已有的 LeRobot v3 导出。LeRobot 数据结构和训练入口有明确的生态约定，能够减少自定义格式带来的适配风险。

## 8. 重新启动 HDF5 需求的验收条件

只有满足以下条件，才建议进入实现阶段：

- 明确唯一或分阶段的目标训练框架；
- 固化 HDF5 内部 schema 和版本号；
- 提供可读取的参考样例；
- 明确语言指令和 task 的存储规则；
- 明确图像、状态、动作的 dtype、shape 和单位；
- 明确缺失数据和失败 episode 的处理方式；
- 提供可自动执行的加载或训练 smoke test；
- 由需求方确认输出文件可被其训练代码读取。

验收不应只包括“文件生成成功”或“能够被 HDF5 Viewer 打开”，而应至少包括：

```text
导出成功
→ 参考加载器成功读取
→ episode 数量一致
→ state/action/image 长度一致
→ 任务和语言字段正确
→ 最小训练或 batch 构建成功
```

## 9. 最终建议

当前不应因为 HDF5 是二进制格式，就认定它比 JSONL 更通用。HDF5 更适合高效存储和训练读取，但跨框架兼容性高度依赖内部 schema；JSONL 更适合作为透明、可审计、可转换的中间格式。

因此，当前项目同时保留 JSONL 到 LeRobot ACT/VLA 的标准链路，并提供已版本化的项目自定义 HDF5 v1 交换格式。若后续要求直接兼容某个训练框架，仍应在本 schema 之上增加独立适配器，并以该框架的参考加载器和训练 smoke test 作为验收依据。
